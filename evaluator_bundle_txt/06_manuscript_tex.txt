\title{A Reproducible Benchmark Suite for Isolating Orchestration Overhead, Schema Prefill Scaling, and KV-Cache Dynamics in Local LLM Agents: Quad-Platform Empirical Evaluation of Llama-3.2-3B on macOS, Linux, and Windows}

\begin{abstract}
As autonomous AI agents shift from remote cloud endpoints to local edge deployment, client runtime execution overhead competes directly with neural weights for unified memory and compute bandwidth. We introduce the \texttt{picoclaw-vs-openclaw-benchmark} suite, an extensible, reproducible benchmarking framework and active schema-pruning toolkit designed to isolate client orchestrator delay ($T_{\text{orch}}$) from neural inference latency ($T_{\text{neural}}$). The framework evaluates four client orchestrator environments---compiled native Go (\texttt{PicoClaw}), TypeScript atop Node.js V8 (\texttt{OpenClaw}), native Bun JavaScriptCore, and reference CPython---interfacing with local \texttt{llama-server} (\texttt{llama.cpp}) serving quantized \texttt{Meta-Llama-3.2-3B-Instruct} (\texttt{Q4\_K\_M}) across four physical testbed environments: Apple Silicon Mac mini M4 (macOS Darwin ARM64), Dell G15 with NVIDIA RTX 3050 (Ubuntu 26.04 LTS Linux x86\_64), Dell G15 with NVIDIA RTX 3050 (Windows 11 x86\_64), and MSI Z97 Intel Core i7-4790K with integrated Intel HD Graphics 4600 (Windows 10/11 x86\_64). Across five standardized workload tiers (W1--W5), the suite evaluates 54 enterprise tools versus 15 minimal equalized tools alongside an active Zero-Copy Dynamic Tool-RAG Schema Pruner ($54 \rightarrow \text{Top-}5$ tools in $<0.35\text{ ms}$). Telemetry captures platform-native counters (Darwin XNU \texttt{libproc}, Linux \texttt{perf\_event\_open}, Win32 \texttt{QueryProcessCycleTime}/PSAPI), electrical sensor rails (Apple SMC, Intel RAPL, NVIDIA NVML), and non-parametric statistical inference (Mann-Whitney $U$ with Holm-Bonferroni control, Cliff's Delta, Vargha-Delaney $\hat{A}_{12}$, Moving Block Bootstrap confidence intervals, adaptive block permutation, and Two One-Sided Equivalence Tests). The suite also provides a portable simulation mode (\texttt{make dry-run}) executing in under ten seconds across macOS, Linux, and Windows without superuser privileges or model weights.
\end{abstract}

\noindent\textbf{Keywords:} AI Agent Orchestration; Benchmarking Framework; Quad-Platform Systems; Apple Silicon M4; Energy-Delay Product; Non-Parametric Statistics; Software Reproducibility.

\section{Motivation and Significance}
\label{sec:motivation}
Autonomous agentic workflows employing the ReAct (Reasoning and Acting) paradigm \cite{yao2023react} require orchestrators to iteratively parse tool schemas, validate arguments, dispatch operating system operations, and format prompts for Large Language Model (LLM) inference \cite{yao2023react, kwon2023vllm}. On unified memory microarchitectures such as Apple Silicon (UMA @ 120 GB/s) and modern x86\_64 host platforms, agent orchestrators share physical DRAM channels with neural inference runtimes (\texttt{llama.cpp}) \cite{williams2009roofline, maricq2018taming}. 

Prior benchmarks predominantly evaluate LLM inference throughput or reasoning accuracy on cloud APIs and aggregate agent task completion \cite{reddi2020mlperf, yao2023react, zheng2023judging}, while recent systems studies highlight the growing need to disentangle client-side runtime bottlenecks from server-side context reuse and prefix-caching dynamics \cite{kwon2023vllm}. Furthermore, expanding enterprise tool catalogs severely inflate prefill latency, motivating dynamic semantic tool retrieval and schema pruning \cite{kwon2023vllm}. Concurrently, software runtime overhead (e.g., garbage collection, context serialization, dynamic schema validation) directly impacts host resource efficiency and the Energy-Delay Product ($\text{EDP} = E \times T$), as investigated in systems energy-proportionality and GPU power studies \cite{barroso2007case, you2023zeus} and foundational systems benchmarking methodologies \cite{kalibera2013rigorous, hoefler2015scientific, maricq2018taming, kuensch1989jackknife}. 

To bridge this gap, we developed \texttt{picoclaw-vs-openclaw-benchmark}, an open-source, extensible framework providing:
\begin{enumerate}
    \item Mathematical isolation of orchestrator delay: $T_{\text{task}} = T_{\text{neural}} + T_{\text{orch}}$, with microsecond precision;
    \item Physical hardware telemetry leveraging phase-isolated Apple SMC shunt sampling alongside validated Darwin XNU \texttt{libproc} instruction/cycle counters (and empirical refutation of uncalibrated \texttt{ri\_billed\_energy} counters \cite{fahad2019comparative, weaver2013nondeterminism}) plus Linux RAPL/NVML/\texttt{perf\_event\_open} and Windows 10/11 Win32 energy/cycle interfaces;
    \item Controlled ablation quantifying the cost of 54 enterprise tools versus an equalized minimal configuration, paired with an active \textbf{Zero-Copy Dynamic Tool-RAG Schema Pruner} ($54 \rightarrow \text{Top-}5$ tools in $<0.35\text{ ms}$) that eliminates $>85\%$ of cold-prefill latency and energy;
    \item Reference cross-language comparison encompassing Go (compiled native), Node.js (JIT V8), native Bun (JavaScriptCore), and Python 3.12 (interpreted reference);
    \item Multi-platform reviewer reproducibility with zero external dependencies and graceful unprivileged non-root fallback.
\end{enumerate}

This benchmarking suite evaluates clean-room, isomorphic reference implementations in Go (\texttt{picoclaw\_orch.go}), Node.js/TypeScript (\texttt{openclaw\_orch.mjs}), Bun JavaScriptCore (\texttt{bun\_jsc\_agent.mjs}), and Python (\texttt{python\_orch.py}) designed to evaluate systems-level trade-offs between Go / Bun (JSC) vs. Node.js (V8) and CPython orchestrators under identical prompts and tool schemas. \subsection{Related Work and Positioning}
Prior benchmarking suites and systems studies address complementary layers of the autonomous LLM execution stack across five principal domains:
\begin{enumerate}[(a)]
    \item \textbf{Agent Response Quality and Multi-Turn Reasoning:} Benchmarks such as ReAct \cite{yao2023react} and MT-Bench / LLM-as-a-Judge \cite{zheng2023judging} evaluate conversational coherence, multi-turn reasoning trajectories, and task completion accuracy, assessing model capability rather than client runtime systems latency or CPU/memory microarchitecture.
    \item \textbf{Inference Server Throughput and Acceleration:} Standardized industry suites such as MLPerf Inference \cite{reddi2020mlperf} evaluate raw token generation throughput and hardware accelerator tail latency ($T_{\text{model}}$), treating the client as an external load injector rather than profiling host-side runtime dispatch loops.
    \item \textbf{Tool Orchestration, Schema Pruning, and Protocol Transport Overhead:} While modern agent frameworks (LangChain, AutoGen, CrewAI) integrate diverse tool catalogs and emerging standards such as the Model Context Protocol (MCP), empirical studies rarely decouple middleware dispatch delay ($T_{\text{orch}} = T_{\text{task}} - T_{\text{neural}}$), serialization cost, and inter-process transport latency (Unix domain sockets vs. loopback HTTP vs. Winsock TCP) from token generation.
    \item \textbf{Energy, Power Telemetry, and Sensor Boundaries:} Systems energy frameworks such as Zeus \cite{you2023zeus}, energy-proportional computing models \cite{barroso2007case}, and computing energy measurement methodologies \cite{fahad2019comparative} investigate accelerator energy dissipation, yet frequently encounter sensor boundary mismatches (e.g., Apple SMC full-SoC instrumentation vs. Intel RAPL package rails excluding motherboard VRMs).
    \item \textbf{KV-Cache Memory Management, Offload, and Memory Bandwidth:} Architectures such as PagedAttention / vLLM \cite{kwon2023vllm} and FlexGen \cite{sheng2023flexgen} optimize server-side memory paging and partial GPU--CPU tensor offload, while analytical models such as the Roofline visual performance model \cite{williams2009roofline} quantify memory bandwidth limits during autoregressive token decode.
\end{enumerate}
Conversely, this benchmark specifically targets the unmeasured boundary between neural inference and host runtime execution by algebraically decoupling $T_{\text{orch}} = T_{\text{task}} - T_{\text{neural}}$ across compiled Go, Node.js V8, Bun JSC, and CPython over four physical hardware/OS testbed profiles while incorporating dynamic schema pruning (Tool-RAG).

From a systems methodology and workload modeling perspective \cite{kalibera2013rigorous, hoefler2015scientific, maricq2018taming, weaver2013nondeterminism, feitelson2015workload, zilberman2020benchmarking}, empirical evaluation requires non-parametric order statistics, dispersion, and randomized blocking. Rank-based procedures such as the Wilcoxon--Mann--Whitney test \cite{mann1947test} lose nominal Type~I error control under unequal distribution shapes \cite{zimmerman1993rank, fagerland2009wilcoxon} and display inflated false-positive rates when sequential trials exhibit positive lag-1 autocorrelation ($r_1 > 0$) induced by hardware thermal throttling or page-cache retention. Our analysis pipeline addresses this directly: contiguous block permutation (\texttt{block\_permutation\_mwu}, $B=5000$) with adaptive block length $b \in \{3, 5, 8, 12\}$ determined by $\max(|r_1|)$ serves as the primary two-sample inference procedure, while analytical $r_1$-VIF variance inflation ($n_{\text{eff}} = n(1-r_1)/(1+r_1)$ \cite{bayley1946effective, yue2004mann}) is retained solely as sensitivity analysis. Dual-session equivalence is assessed via Moving Block Bootstrap (MBB, $B=10{,}000$, Künsch \cite{kuensch1989jackknife}) TOST \cite{schuirmann1987comparison, lakens2017equivalence} across $b \in \{2, 3, 5, 8, 12, \text{adaptive}\}$ and evaluated under both fixed ($\pm 5.0\text{ ms}$) and proportional SESOI. \subsection{Software Architecture: Generic Framework vs. Empirical Case Study}
The software explicitly separates the \textbf{generic, reusable benchmarking harness} (\texttt{AgentOrchestratorAdapter}, \texttt{SMCPowerMonitor}, \texttt{LinuxRAPLMonitor}, \texttt{protocol\_invariants}, and deterministic workload synthesis) from the \textbf{empirical multi-runtime case study} (\texttt{go\_orchestrator}, \texttt{node\_orchestrator}, \texttt{python\_reference\_agent}, and \texttt{bun\_jsc\_orchestrator}):
\begin{itemize}
    \item \textbf{Generic Adapter Contract (\texttt{AgentOrchestratorAdapter}) and Case-Study Runtimes:} Abstract strategy (\texttt{benchmark/adapters/base.py}) defining standardized lifecycle hooks: \texttt{setup()}, \texttt{cold\_start\_cmd()} (benchmarked via statistical sampling \cite{kalibera2013rigorous}), \texttt{run\_workload(w\_id)}, and \texttt{teardown()}. Registry keys use neutral architecture-first canonical identifiers (with backward-compatible reference aliases):
    \begin{itemize}
        \item \texttt{GoNativeOrchestratorAdapter} (\texttt{go\_orchestrator} / alias \texttt{picoclaw}): Compiled native static binary written in Go (Go 1.23.2 Mach-O ARM64 on macOS, Go 1.23.3 PE AMD64 on Windows 11, Go 1.26.8 ELF x86\_64 on Linux, and native PE x86\_64 on Windows 10 iGPU; \texttt{benchmark/picoclaw\_orch.go}, supporting both standard 15-tool parity and \texttt{go\_orchestrator\_tool\_rag} $54 \rightarrow \text{Top-}5$ dynamic vector schema pruning);
        \item \texttt{NodeV8OrchestratorAdapter} (\texttt{node\_orchestrator\_minimal|full} / aliases \texttt{openclaw\_minimal|full}): Node.js / V8 runtime (v26.12.1 on macOS, v18.20.8 on Linux, v20.18.1 on Windows 11, and v22.23.5 on Windows 10 iGPU; \texttt{benchmark/openclaw\_orch.mjs}) evaluating \texttt{minimal} (15 tools), \texttt{full} (54 tools), and \texttt{node\_orchestrator\_tool\_rag} ($54 \rightarrow \text{Top-}5$ dynamic vector schema pruning) schema loads;
        \item \texttt{PythonReferenceAdapter} (\texttt{python\_reference\_agent} / alias \texttt{python\_native}): Interpreted reference agent in CPython (3.9.6 on macOS, 3.12.10/3.12.16 on Windows, 3.14.4 on Linux; \texttt{benchmark/python\_orch.py}) with NumPy vector projections and Tool-RAG support;
        \item \texttt{BunJSCOrchestratorAdapter} (\texttt{bun\_jsc\_orchestrator} / alias \texttt{bun\_minimal}): Independent fourth orchestrator runtime executing a dedicated JavaScriptCore worker (\texttt{benchmark/bun\_jsc\_agent.mjs}) natively atop Bun v1.4.4 (\texttt{darwin-aarch64}, Linux x86\_64, and Windows 11) and Bun v1.4.5 (Windows 10 Intel iGPU), utilizing WebKit JavaScriptCore with native \texttt{Bun.file()} zero-copy I/O, \texttt{Bun.nanoseconds()} monotonic timers, and native JSC \texttt{fetch} (verified \texttt{is\_fallback\_node=false});
        \item \texttt{LocalLLMBaselineAdapter} (\texttt{local\_llm\_baseline} / alias \texttt{neural\_baseline}): Direct HTTP streaming pass-through measuring zero-orchestrator neural inference latency.
    \end{itemize}
    \item \textbf{Automated Protocol Invariant Validator (\texttt{benchmark/protocol\_invariants.py}):} Enforces seven fail-fast experimental invariants prior to statistical aggregation: (1) positive token counts ($\texttt{prompt\_tokens} > 0$, $\texttt{completion\_tokens} > 0$), (2) exact byte-and-token parity across all 15-tool arms within each workload when \texttt{require\_equalized\_tokens=True}, (3) valid termination states ($\texttt{finish\_reason} \in \{\texttt{stop}, \texttt{tool\_calls}, \texttt{length}\}$), (4) $\texttt{http\_status} = 200$, (5) exact sample counts ($N=600$, $n=30$ per cell), (6) non-empty \texttt{session\_id} and \texttt{git\_commit} provenance, and (7) positive physical net energy ($\texttt{energy\_net\_above\_idle\_j} > 0$) on SMC hardware runs.
    \item \textbf{Deterministic Workload Generator (\texttt{data/workload\_data/}):} Provides five standardized workload tiers (W1--W5):
    \begin{itemize}
        \item \textbf{W1 (Simple Reflection):} In-memory synthesis (64 tokens);
        \item \textbf{W2 (3-Step Tool Chain):} APFS filesystem inspection, regex parsing, and numerical statistics (128 tokens);
        \item \textbf{W3 (Vector RAG):} Cosine similarity ranking over 10,000 document chunks via a deterministic projection head (256 tokens);
        \item \textbf{W4 (10-Turn ReAct):} Multi-step autonomous decision loop executing 10 tool invocations (640 tokens);
        \item \textbf{W5 (Enterprise Cross-Domain Workflow --- LangChain Core + SQLite):} Multi-table enterprise SQLite budget, SLA, and compliance query workflow evaluated across all four hardware/OS environments (Table~\ref{tab:w5_enterprise_workload}), with the \texttt{python\_native} LangChain Core prototype arm diagnostically segregated in Table~\ref{tab:w5_enterprise_workload} Part~B (and excluded from W5 latency/energy/TOST comparisons) due to schema validation failure and confounded/truncated prompts.
    \end{itemize}
    \item \textbf{Hardware and Kernel Telemetry Engine:} Combines Apple SMC \texttt{powermetrics} (50 ms milliwatt current sampling) with unprivileged Darwin kernel \texttt{proc\_pid\_rusage} (recording resident set size, retired CPU instructions, and core cycles).
\end{itemize}

The framework's extensible design is demonstrated in Listing~\ref{lst:rust_adapter}, showing how a new native agent orchestrator (e.g., \texttt{RustRigAdapter} targeting a high-performance compiled Rust binary) can be integrated in under 35 lines of Python code:

\begin{lstlisting}[language=Python, caption={Extending the benchmark suite with a native Rust agent orchestrator adapter (\texttt{rust\_rig\_adapter.py}).}, label={lst:rust_adapter}]
from benchmark.adapters.base import AgentOrchestratorAdapter
from benchmark.telemetry import run_subprocess_with_rusage
import os, json

class RustRigAdapter(AgentOrchestratorAdapter):
    """Native Rust agent orchestrator adapter implementing the lifecycle contract."""
    def __init__(self, repo_dir: str):
        super().__init__(
            name="RustRig",
            runtime="Rust 1.80 (Native Mach-O ARM64)",
            language="Rust",
            mode="native_release"
        )
        self.bin_path = os.path.join(repo_dir, "bin", "rust_rig_agent")

    def setup(self) -> bool:
        return os.path.exists(self.bin_path)

    def cold_start_cmd(self) -> list[str]:
        return [self.bin_path, "--version"]

    def run_workload(self, workload_id: str, prompt: str = "", iterations: int = 1) -> dict:
        cmd = [self.bin_path, "--workload", workload_id, "--reps", str(iterations)]
        stdout, stderr, rc, hw_stats = run_subprocess_with_rusage(cmd)
        if rc != 0:
            raise RuntimeError(f"RustRig execution failed: {stderr}")
        res = json.loads(stdout.strip())
        return {**res[0], **hw_stats}
\end{lstlisting}

\subsection{Software Functionalities}
The analysis engine (\texttt{benchmark/analyze\_results.py}) computes formal computer systems metrics and publication-ready LaTeX tables:
\begin{itemize}
    \item \textbf{Energy-Delay Product (EDP):} Computes total energy $E = \int P(t) dt$ and active energy above quiescent baseline, yielding $\text{EDP} = E \times T_{\text{task}}$ ($\text{J}\cdot\text{s}$) \cite{barroso2007case, you2023zeus}, alongside Joules per generated token.
    \item \textbf{Non-Parametric Central Tendency and Dispersion:} Reports median and Interquartile Range ($\text{IQR} = Q_3 - Q_1$) to prevent outlier distortion from GPU prefill and garbage collection events, supplemented by empirical mean $\pm$ standard deviation and 95th percentile ($p_{95}$) tail latency.
    \item \textbf{Statistical Hypothesis Testing and Effect Sizes:} Conducts two-sided Mann-Whitney $U$ tests \cite{mann1947test} with $r_1$-adjusted effective sample size ($n_{\text{eff}}$) variance correction for positively autocorrelated cells \cite{bayley1946effective, yue2004mann, zimmerman1993rank, fagerland2009wilcoxon} (supplemented by Kruskal-Wallis rank variance checks \cite{kruskal1952use}), adjusted for multiple comparisons via the Holm-Bonferroni step-down procedure \cite{holm1979simple}, Cliff's Delta $d \in [-1, 1]$ \cite{cliff1993dominance}, and Vargha-Delaney $\hat{A}_{12} \in [0, 1]$ \cite{vargha2000critique}, alongside Moving Block Bootstrap 95\% confidence intervals for serially dependent observations \cite{kuensch1989jackknife} and Two One-Sided Equivalence Tests (TOST) with pre-specified smallest effect sizes of interest (SESOI) and 90\% block-bootstrap confidence intervals \cite{schuirmann1987comparison, lakens2017equivalence} for dual-session contrast replication.
\end{itemize}

\paragraph{Primary Physical Memory Metric (\texttt{Peak Physical Footprint})}
Throughout this study, we adopt \textbf{Peak Physical Footprint} (\texttt{proc\_peak\_phys\_mb}, extracted directly from Darwin XNU's \texttt{ri\_lifetime\_max\_phys\_footprint} counter in \texttt{RUSAGE\_INFO\_V4}) as our single primary metric for host memory consumption. Methodologically, \texttt{ri\_lifetime\_max\_phys\_footprint} measures the exact lifetime peak of anonymous dirty, wired, and compressed physical RAM pages exclusively allocated by the process—the exact quantity used by the Darwin kernel jetsam memory manager to enforce physical UMA limits—whereas POSIX \texttt{ru\_maxrss} (Peak RSS) reports the virtual resident set size, which conflates private heap allocations with clean, read-only system shared libraries (\texttt{dyld} shared cache) mapped across all processes. To prevent ambiguity, all architectural comparisons and decision rules in the text report \texttt{Peak Physical Footprint} (\texttt{proc\_peak\_phys\_mb}) exclusively.

\paragraph{Distinction Between Warm Process Execution and Warm KV-Cache Regime}
We explicitly distinguish between \textit{Warm Process Execution} and the \textit{Warm KV-Cache Regime (Regime B)}. In Warm Process Execution, client-side agent runtimes (e.g., Node.js V8 JIT compiler, CPython interpreter bytecode caches, or Go runtime threads) have completed initial binary loading, module imports, and heap allocation, eliminating cold interpreter bootstrap overheads (characterized separately via \texttt{hyperfine} cold-start profiling). In contrast, the Warm KV-Cache Regime (Regime B) specifically denotes that the server-side neural inference daemon (\texttt{llama-server}) retains pre-computed Key-Value attention states for recurring system prompts and tool schemas in GPU memory (\texttt{cache\_prompt=true}), avoiding redundant prompt attention prefill calculations across dialogue turns.

\subsection{Hardware Constraints, Permissions, and Two-Stage Energy Deconvolution}
In unified-memory System-on-Chip (SoC) architectures such as Apple Silicon M4, physical electrical shunt sensors managed by the System Management Controller (SMC) instrument aggregate hardware power rails (CPU clusters, Metal GPU, and ANE) at the package level rather than individual operating system processes \cite{fahad2019comparative}. Consequently, isolating exclusive analog Joules for a single POSIX process during concurrent CPU--GPU execution is physically unobservable at the hardware shunt layer. Following established energy-benchmarking methodology for machine learning systems \cite{you2023zeus, fahad2019comparative}, our harness resolves this architectural constraint via a two-stage hardware validation protocol: (i) phase-isolated direct hardware measurement of client-side tool execution on the Apple SMC \texttt{CPU Power} rail ($E_{\text{CPU, net}}$) with the Metal GPU idle ($P_{\text{GPU}} \approx 0\text{ W}$) alongside paired baseline subtraction ($\Delta E_{\text{net}}$) against \texttt{neural\_baseline}, and (ii) empirical cross-validation of Darwin XNU \texttt{proc\_pid\_rusage} counters against physical SMC current shunts. Crucially, our empirical validation establishes a formal \textbf{Negative Result for Darwin XNU \texttt{ri\_billed\_energy}}: across 120 isolated CPU trials, uncalibrated \texttt{ri\_billed\_energy} exhibits zero global correlation with physical SMC \texttt{CPU Power} rail Joules (Pearson $r = -0.0510, p = 0.580$; centered $\text{OLS } R^2 = -0.676$ relative to the sample mean), performing worse than a constant mean predictor and overestimating CPython energy by $10\text{--}30\times$ due to internal XNU scheduler QoS/thread-weighting heuristics, directly corroborating prior findings by Fahad et al.~\cite{fahad2019comparative} on the unreliability of uncalibrated on-chip energy estimation models (which can incur $73\%$ average and up to $300\%$ maximum error). Conversely, physical duration (\texttt{t\_exec\_ms}, $r = 0.992, R^2 = 0.949$), retired CPU instructions (\texttt{proc\_instructions}, $r = 0.985, R^2 = 0.955$), and core cycles (\texttt{proc\_cycles}, $r = 0.991, R^2 = 0.945$) serve as rigorously validated physical CPU energy proxies.

Direct access to Apple SMC hardware sensors via \texttt{powermetrics} requires elevated \texttt{root} privileges due to Darwin XNU kernel protections against microarchitectural power side-channel vulnerabilities. Crucially, the benchmark runner enforces privilege isolation: all evaluated agent runtimes, orchestrator subprocesses, and the \texttt{llama-server} neural daemon execute in unprivileged user space. When administrative privileges are absent, the telemetry layer degrades gracefully without synthetic estimation, recording latency, memory footprint, and \texttt{libproc} counters while marking electrical energy fields as unavailable (\texttt{N/A}).

Crucially, when isolating runtime orchestrator overhead ($T_{\text{orch}}$) and separating client-side dispatch delay ($T_{\text{dispatch}}$) from HTTP transport latency ($T_{\text{http}}$), the architectural characteristics of the three language runtimes become clearly measurable:
\begin{itemize}
    \item \textbf{Go Native (\texttt{PicoClaw}):} Achieves the lowest median orchestrator delay of $T_{\text{orch}} = \WTwoPicoOrchMedian\text{ ms}$ (mean $\WTwoPicoOrchMean\text{ ms}$), combining $T_{\text{dispatch}} = 1.78\text{ ms}$ with $T_{\text{http}} \approx 3.80\text{ ms}$ powered by Go's native \texttt{net/http} stack and non-blocking goroutines.

\end{itemize}
Overall, Go achieves $\WTwoOrchSpeedup\times$ lower orchestrator latency ($T_{\text{orch}}$) than Node.js Minimal. \subsection{Controlled Tool Catalog Schema Prefill and KV-Cache Reuse Characterization (\texttt{llama.cpp} / Metal GPU)}
To address the critical distinction between orchestrator-induced dispatch delay ($T_{\text{orch}}$) and prompt-prefill attention computation ($T_{\text{prefill}}$) on unified memory architectures \cite{kwon2023vllm, williams2009roofline}, we conducted a controlled schema ablation directly against the local inference engine (\texttt{llama.cpp}) across 8 tool catalog sizes $T \in \{0, 5, 10, 15, 25, 40, 54, 100\}$ and prompt-cache configurations ($\texttt{cache\_prompt} \in \{\text{false}, \text{true}\}$, $n=30$ independent physical evaluations per cell following 3 priming warmups). This controlled experiment explicitly characterizes the prefill scaling behavior of the underlying Metal GPU inference server under progressive tool schema injection ($0$ to $100$ schemas), providing an empirical baseline for the impact of prompt bloat independently of host orchestrator execution. The consolidated empirical results are presented in Table~\ref{tab:prefill_ablation}.

\input{../results/publication_campaign/tables/table_prefill_ablation.tex}

As documented in Table~\ref{tab:prefill_ablation}, in-memory schema serialization and dispatch delay ($T_{\text{dispatch}}$) remains negligible ($< 2\text{ ms}$). However, un-cached prompt prefill latency ($T_{\text{prefill}}$) on the Metal GPU scales steeply with catalog dimension: prefill latency increases from approximately $128\text{ ms}$ at $0$ tools ($60$ tokens) to over $4{,}400\text{ ms}$ at $15$ tools ($2{,}081$ tokens), $17{,}900\text{ ms}$ at $54$ tools ($7{,}190$ tokens), and reaching nearly $39{,}000\text{ ms}$ at $100$ tools ($13{,}216$ prompt tokens), dominating total execution duration.

Regression analysis over the empirical trials in \texttt{prefill\_ablation.jsonl} confirms super-linear scaling: a power-law fit ($T_{\text{prefill}} = 0.3197 \cdot N^{1.2342}$ with 95\% CI $\alpha \in [1.2324, 1.2360]$, $R^2 = 0.9993$, $\text{AIC}_c = 99.25$) and quadratic model ($T_{\text{prefill}} = 7.895 \times 10^{-5} N^2 + 1.9201 N + 17.36\text{ ms}$, $R^2 = 0.99999$, $\text{AIC}_c = 68.88$) decisively outperform linear prefill approximations ($R^2 = 0.9889$, $\text{AIC}_c = 120.84$), reflecting the combined super-linear prefill cost of transformer self-attention, prompt batching (\texttt{ubatch}), and Metal kernel scheduling in \texttt{llama.cpp} prior to KV-cache allocation (where the narrow bootstrap CI $\alpha \in [1.2324, 1.2360]$ reflects intra-session curve-fit precision). Crucially, activating KV-cache reuse ($\texttt{cache\_prompt} = \text{true}$) bypasses redundant attention evaluations across identical schema prefixes, unlocking a massive $5.5\times$ to $946.5\times$ speedup on prefill latency (reducing TTFT to sub-second levels across all tool catalog dimensions). This empirical characterization confirms that stock enterprise multi-tool agent schemas impair execution primarily through super-linear neural attention prefill scaling rather than host orchestrator delay \cite{kwon2023vllm}.

To provide an active software-level solution to enterprise schema bloat alongside server-side KV-cache retention, we implemented and evaluated a \textbf{Zero-Copy Dynamic Tool-RAG Schema Pruner} (\texttt{OPENCLAW\_MODE="tool\_rag"}) inside the Go, Node.js V8, and Python orchestrator workers, motivated by active schema retrieval and prompt bloat mitigation \cite{kwon2023vllm}. Prior to HTTP payload serialization, the orchestrator initializes the full 54-tool corporate catalog ($N_{\text{schemas}} = 54$) and executes an in-memory 384-dimensional cosine similarity dot-product against the workload query embedding to select only the $\text{Top-}K$ ($K=5$) semantically relevant tools. Table~\ref{tab:tool_rag_mitigation} reports the physical evaluation across W1--W4 under both Regime A and Regime B ($n=30$ physical trials per condition with continuous SMC power telemetry). Semantic pruning adds merely $0.033\text{ to }0.038\text{ ms}$ per turn in Go ($0.382\text{ ms}$ across 10 turns in W4) and $0.286\text{ to }0.427\text{ ms}$ per turn in Node.js V8 ($3.330\text{--}4.268\text{ ms}$ across 10 turns in W4) while shrinking the serialized prompt from $7{,}067\text{--}7{,}499$ tokens to $893$ tokens in W1 ($72{,}120\text{--}76{,}440$ to $9{,}197\text{--}10{,}380$ tokens across 10 turns in W4). Under cold prefill (Regime A), active Tool-RAG pruning eliminates $85.5\%\text{ to }87.2\%$ of end-to-end latency and $85.6\%\text{ to }87.8\%$ of net electrical energy relative to the unpruned 54-tool catalog (and reduces latency by $50.9\%\text{ to }54.6\%$ even relative to the static 15-tool catalog), while in Regime B it reduces active KV-cache attention span by $21.1\%\text{ to }37.9\%$ vs. 54 tools, outperforming even static 15-tool execution ($952.4\text{ ms}$ vs. $1033.5\text{ ms}$ in W1; $8334.2\text{--}8358.8\text{ ms}$ vs. $8605.5\text{ ms}$ in W4).

\subsection{Comparative Analysis: Cold Prefill Regime vs. Realistic KV-Cache Reuse Regime}
To evaluate runtime performance under production deployment scenarios where common tool catalogs and system prompts persist across agent turns, we conducted a companion campaign of 600 evaluated physical trials (60 priming warmups excluded) under active KV-cache prefix retention (\texttt{cache\_prompt=true}, $n=30$ independent physical evaluations per condition, block-isolated to eliminate single-slot cache thrashing in \texttt{llama-server}). The empirical results are presented in Table~\ref{tab:evaluation_warm_cache_m4}.

\input{../results/publication_campaign/tables/table_warm_cache.tex}

Contrasting the cold prefill regime (Regime A, Table~\ref{tab:evaluation_ablation_m4}) and the warm cache regime (Regime B, Table~\ref{tab:evaluation_warm_cache_m4}) reveals the operational trade-offs of edge agent execution:
\begin{itemize}
    \item \textbf{Regime A (\texttt{cache\_prompt=false}):} Cold prompt attention prefill on the Metal GPU accounts for $>75\%$ of end-to-end task latency across all configurations. Because the GPU saturates package power at $\approx 16\text{ W}$ during attention computation, total latency and active energy remain dominated by neural matrix evaluation, producing near-parity in wall-clock duration between host runtimes.
    \item \textbf{Regime B (\texttt{cache\_prompt=true}) and Physical KV-Cache Thrashing vs. Slot Isolation Ablation:} When prompt prefill is amortized through verified block-isolated KV-cache prefix retention in \texttt{llama-server} ($\text{Cache Hit}$ of $99.9\%$ to $100.0\%$ in W1--W3 and $97.7\%$ to $99.3\%$ in W4; 20 randomized condition blocks with 3 priming warmups and 30 consecutive evaluations per block in single-slot \texttt{-np 1}), overall task duration drops dramatically: in W2, task latency falls to sub-second levels ($741.2\text{ ms}$ for Go Native, $743.4\text{ ms}$ for Python 3.12, $752.8\text{ ms}$ for Node.js Minimal, and $937.7\text{ ms}$ for Node.js Full---a $21.1\times$ reduction for the 54-tool catalog compared to un-cached cold execution). Table~\ref{tab:evaluation_warm_cache_m4} explicitly decomposes total prompt tokens into cached prefix tokens and newly evaluated uncached tokens (\texttt{Tot / Cached / New}) alongside median \texttt{TTFT / ITL}, characterizing five fundamental KV-cache operational behaviors: (i) \textit{cold cache} (\texttt{cache\_prompt=false}), where all $N_{\text{prompt}}$ tokens undergo full attention evaluation ($\texttt{cached\_tokens}=0$, $\text{TTFT} > 4.4\text{ s}$); (ii) \textit{warm cache with identical prefix} (\texttt{cache\_prompt=true} intra-block), where consecutive trials reuse $99.9\%$ of the prefix ($2{,}152 / 2{,}153$ in W1, $2{,}176 / 2{,}177$ in W2, $2{,}409 / 2{,}410$ in W3) and evaluate only $\texttt{New}=1$ boundary token ($\text{TTFT} = 232.4\text{--}269.5\text{ ms}$, $\text{ITL} = 16.24\text{--}20.14\text{ ms}$); (iii) \textit{prefix switching across condition blocks}, where transitioning between 15-tool, 54-tool, or Top-5 schemas triggers a prefix miss absorbed by the 3 priming warmups; (iv) \textit{interleaved prefix thrashing vs. isolated slot retention} (\texttt{scripts/run\_kv\_cache\_thrashing\_ablation.py}, archived in \texttt{kv\_cache\_thrashing\_trials.jsonl} and \texttt{kv\_cache\_thrashing\_summary.json}, $n=30$ physical evaluations per regime in W2): when alternating every request between two unisolated agents with distinct system headers and tool catalogs (15 schemas [$2{,}177$ tokens] vs. 54 schemas [$7{,}091$ tokens]) sharing a single KV-cache slot (\texttt{-np 1}, Regime T2), the active prefix diverges right after the 32-token template preamble ($\texttt{cached\_tokens} = 31.9\text{--}32.0$, $\text{Cache Hit} = 0.96\%$ overall and $0.45\%$ on 54 schemas vs. $99.95\%\text{--}99.99\%$ under isolated prefix retention in Regime T3), inflicting a $7.37\times$ task latency penalty on the 15-tool agent ($5472.9\text{ ms}$ vs. $742.3\text{ ms}$) and a $19.91\times$ task latency penalty on the 54-tool agent ($18551.4\text{ ms}$ vs. $931.9\text{ ms}$, corresponding to a $531.3\times$ prefill latency penalty [$17613.6\text{ ms}$ vs. $33.15\text{ ms}$] and escalating mean net energy from $11.51\text{ J}$ to $313.07\text{ J}$); and (v) \textit{prefix invalidation and multi-turn growth} in W4, where cumulative 10-turn tokens reach $22{,}980$ ($22{,}457$ cached [$97.7\%$] and $523$ newly evaluated [$\approx 52.3\text{ tokens/turn}$]). Across W1--W4, Go Native, Python 3.12, and Node.js Minimal remain within $-0.92\%$ to $+5.83\%$ in median ($-1.14\%$ to $+5.85\%$ in mean; and within $-0.92\%$ to $+1.79\%$ across W1, W2, and W4) of the Direct Local LLM Baseline ($739.6\text{ ms}$ median in W2; $8503.6\text{ ms}$ in W4). Crucially, under this amortized prefill regime, host orchestrator overhead is no longer masked by GPU attention stalls, elevating the relative orchestration share ($\Phi_{\text{orch}} = T_{\text{orch}} / T_{\text{task}}$) to clearly measurable intervals between \PhiOrchFifteenMin{} and \PhiOrchFifteenMax{} ($T_{\text{dispatch}} = 1.78\text{ ms}$ and $T_{\text{http}} = 3.36\text{ ms}$ for Go; $T_{\text{dispatch}} = 1.04\text{ ms}$ and $T_{\text{http}} = 9.85\text{ ms}$ for Python; $T_{\text{dispatch}} = 1.25\text{ ms}$ and $T_{\text{http}} = 19.02\text{ ms}$ for Node.js Minimal in W2), demonstrating that language runtime efficiency becomes directly measurable in I/O and vector-intensive workloads (W2--W3) while remaining within server timing noise ($\pm 1\text{--}2\%$) in W1 and W4. Furthermore, formal sensitivity and outlier analysis (\texttt{sensitivity\_and\_outlier\_analysis.json}) applying pre-registered Tukey fences ($[Q_1 - 1.5\,\text{IQR}, Q_3 + 1.5\,\text{IQR}]$) and $5\%$ trimmed means across all 40 experimental blocks ($1{,}200$ trials) confirms that only $2.67\%$ ($16/600$) of Regime A trials and $1.83\%$ ($11/600$) of Regime B trials are Tukey outliers ($\le 3.3\%$), and removing all outliers shifts cell medians by at most $0.075\%$ in Regime A and $0.094\%$ in Regime B ($< 0.8\%$), demonstrating that no statistical conclusion depends on extreme observations; simultaneously, active electrical power decomposition ($\bar{P}_{\text{net}} = E_{\text{net}} / T_{\text{task}}$) separates high-power GPU attention prefill in Regime A ($\bar{P}_{\text{net}} = 15.86 \pm 0.40\text{ W}$, median $\texttt{prompt\_ms} = 5331.9\text{ ms}$ vs. $\texttt{predicted\_ms} = 718.0\text{ ms}$) from bandwidth-bound autoregressive decode in Regime B ($\bar{P}_{\text{net}} = 13.04 \pm 0.81\text{ W}$, median $\texttt{prompt\_ms} = 245.5\text{ ms}$ vs. $\texttt{predicted\_ms} = 774.7\text{ ms}$).
\end{itemize}

\subsection{Principal Component Analysis (PCA) Variance Decomposition and Inter-Session Replication}
To orthogonalize performance metrics and isolate the latent dimensions governing agent orchestration, Table~\ref{tab:pca_loadings} presents the Principal Component Analysis (PCA) variance decomposition across 12 systems telemetry dimensions for both execution regimes ($N=480$ evaluated trials per regime across \texttt{picoclaw}, \texttt{openclaw\_minimal}, \texttt{openclaw\_full}, and \texttt{python\_native}; excluding \texttt{neural\_baseline} because its structural zeros in $T_{\text{orch}}$, $T_{\text{disp}}$, and client-side memory metrics introduce collinear rank-deficiency in covariance decomposition). Within-workload standardized PCA further confirms that host microarchitectural footprints and dispatch delays form orthogonal components invariant to global prompt scale. Furthermore, to quantify cross-session thermal/OS drift and evaluate an independent fourth orchestrator runtime (\texttt{BunJSCOrchestratorAdapter}, executing \texttt{benchmark/bun\_jsc\_agent.mjs} atop \textbf{Bun v1.4.4}, \texttt{darwin-aarch64}, WebKit JavaScriptCore), we executed an independent inter-session physical replication (\texttt{scripts/run\_inter\_session\_replication.py}, Session 2, \texttt{seed=99}, $n=30$ evaluations $+ 3$ primings per randomized condition block with a single continuous 50~ms SMC daemon, archived in \texttt{inter\_session\_trials.jsonl} and \texttt{inter\_session\_replication.json}). Crucially, comparing Session 1 and Session 2 reveals that absolute end-to-end latency ($T_{\text{task}}$) exhibits an inter-session relative difference of $0.22\%$ to $3.32\%$ (mean $1.62\%$, pooled $\text{CV} = 1.15\%$, and up to $\sim 3\%\text{--}10\%$ across multi-hour sessions) due to ambient thermal equilibrium and Metal GPU clock boosting, which is comparable to or exceeds the small intra-session differences ($-1.14\%$ to $+3.48\%$ in W1, W2, and W4) observed between Go, Python, Node.js V8, and native Bun JSC. Consequently, end-to-end task latency ($T_{\text{task}}$) comparisons across language runtimes are statistically valid solely within a randomized intra-session block design, and small differences ($<10\%$) in W1, W2, and W4 do not represent a persistent cross-session wall-clock advantage (with W4 $T_{\text{task}}$ differences converging within $-1.57\%$ to $+1.08\%$ across sessions). The sole exception in end-to-end latency is W3 (Vector RAG), where Go's scalar dot-product latency penalty relative to vectorized BLAS/SIMD routines replicates consistently across sessions ($+5.85\%$ vs. \texttt{neural\_baseline} in Session 1 and $+5.41\%$ in Session 2), alongside all isolated host microarchitectural metrics ($T_{\text{orch}}$, \texttt{Peak Phys RAM}, retired CPU instructions, and core cycles). Notably, the independent \textbf{Bun JSC Orchestrator} (\texttt{benchmark/bun\_jsc\_agent.mjs}, leveraging \texttt{Bun.file()}, \texttt{Bun.nanoseconds()}, and native JSC \texttt{fetch}) achieves substantially lower host overhead than Node.js V8 across W1--W4 ($T_{\text{orch}} = 3.65\text{ ms}$ in W1, $4.88\text{ ms}$ in W2, $18.09\text{ ms}$ [$T_{\text{disp}} = 14.40\text{ ms}$] in W3, and $48.74\text{ ms}$ in W4; $\text{Peak Phys RAM} = 7.32\text{--}9.54\text{ MB}$ in W1/W2/W4 and $35.97\text{ MB}$ in W3; retiring $86.7 \times 10^6$ to $368.6 \times 10^6$ instructions), closely approaching compiled Go on host footprint while remaining within $-0.65\%$ to $+2.69\%$ of \texttt{neural\_baseline} task latency in W1, W2, and W4 ($+3.49\%$ in W3).

\input{../results/publication_campaign/tables/table_pca_loadings.tex}

Across both regimes, the first three principal components ($\text{PC}_1$, $\text{PC}_2$, and $\text{PC}_3$) account for more than $90\%$ of total system variance ($89.7\%$ in Regime A and $97.1\%$ in Regime B):
\begin{itemize}
    \item \textbf{$\text{PC}_1$ (Neural Attention Prefill and Energy Dissipation):} Explains $54.2\%$ of variance in Regime A and $61.4\%$ in Regime B, grouping prompt token length ($N_{\text{prompt}}$), inference latency ($T_{\text{neural}}$), task duration ($T_{\text{task}}$), net energy ($E_{\text{net}}$), and EDP with nearly identical positive factor loadings ($+0.34$ to $+0.36$, each contributing $11.8\%$ to $12.9\%$). This axis directly quantifies the dominant cost of neural matrix evaluation on the Metal GPU.
    \item \textbf{$\text{PC}_2$ (Host Runtime Microarchitectural Footprint):} Explains $24.0\%$ of variance in Regime A and $26.8\%$ in Regime B, isolating the client-side execution cost. The dominant contributors are physical DRAM resident footprint ($\text{PhysRAM}$, $27.1\%\text{--}27.9\%$), virtual memory ($\text{RSS}$, $22.5\%\text{--}26.6\%$), retired CPU instructions ($\text{Instr}$, $17.3\%\text{--}21.1\%$), and CPU cycles ($6.4\%\text{--}11.1\%$), all showing strong positive loadings ($+0.25$ to $+0.53$) while neural latency and energy contribute negligible or negative loadings. This demonstrates that host memory and instruction retirement decouple orthogonally from GPU prompt prefill.
    \item \textbf{$\text{PC}_3$ (Tool Dispatch and I/O Serialization):} Explains $11.5\%$ of variance in Regime A and $8.8\%$ in Regime B. In Regime B, where prompt prefill latency is neutralized by deterministic KV-cache retention, tool dispatch latency ($T_{\text{disp}}$) accounts for $82.4\%$ of $\text{PC}_3$ with a loading of $+0.908$, isolating the compute and serialization efficiency of client-side tool execution routines (e.g., in-process cosine similarity in W3).
\end{itemize}
Crucially, comparing factor loadings between regimes illustrates how KV-cache amortization alters systems dynamics: under cold prefill (Regime A), orchestrator overhead ($T_{\text{orch}}$) and HTTP round-trip ($T_{\text{http}}$) project onto $\text{PC}_3$ ($34.5\%$ and $30.5\%$ contribution) because they are masked by GPU prefill stalls; under warm KV-cache (Regime B), HTTP and multi-turn orchestration scale directly with dialogue turn count, shifting into $\text{PC}_1$ ($13.2\%$ and $12.9\%$), while pure tool computation ($T_{\text{disp}}$) becomes the sole discriminative factor in $\text{PC}_3$.

\subsection{Key Findings, Hardware Microarchitecture, and Effect Sizes}
Across all 600 physical trials on the Apple Silicon M4 testbed, three core empirical conclusions emerge:
\begin{enumerate}
    \item \textbf{Microarchitectural Efficiency:} Hardware performance counters captured via Darwin XNU kernel \texttt{libproc} reveal that PicoClaw executes an average of $\PicoInstructionsMeanM \times 10^6$ retired CPU instructions and $\PicoCyclesMeanM \times 10^6$ CPU cycles, compared to $\OpenMinInstructionsMeanM \times 10^6$ instructions ($\InstructionOverheadRatio\times$ overhead) and $\OpenMinCyclesMeanM \times 10^6$ cycles ($\CyclesOverheadRatio\times$ overhead) for OpenClaw Minimal.
    \item \textbf{Physical DRAM Footprint Reduction (\texttt{Peak Physical Footprint}):} Lifetime peak physical footprint (\texttt{proc\_peak\_phys\_mb}, extracted from Darwin XNU's \texttt{ri\_lifetime\_max\_phys\_footprint}) confirms that PicoClaw allocates only $4.2\text{--}45.5\text{ MB}$ across W1--W4 (averaging $\PicoPeakPhysMean\text{ MB}$ overall, rising to $45.5\text{ MB}$ only during 10,000-vector cosine dot products in W3), compared to $37.5\text{--}67.1\text{ MB}$ (averaging $\OpenMinPeakPhysMean\text{ MB}$) for Node.js V8---a $\PeakPhysReductionMinRatio\times$ to $\PeakPhysReductionMaxRatio\times$ reduction in physical DRAM allocation ($\PeakPhysLeanerRatio\times$ leaner on global average).
    \item \textbf{Tool Catalog Ablation and EDP Efficiency (Dual-Regime Dynamics):} Evaluating 54 enterprise schemas (OpenClaw Full) against 15 schemas (Minimal) reveals severe prompt bloat: W1 mean latency balloons from $\WOneOpenMinMean\text{ ms}$ to $\WOneOpenFullMean\text{ ms}$, while mean energy escalates from $\WOneOpenMinEnergy\text{ J}$ to $\WOneOpenFullEnergy\text{ J}$ ($\WOneEnergyBloatRatio\times$). In the 10-turn autonomous ReAct loop (W4) under Regime A, OpenClaw Full expends $\WFourOpenFullEnergy\text{ J}$ with an $\text{EDP}$ of $\WFourOpenFullEDP\text{ J}\cdot\text{s}$ ($\WFourOpenFullMedian\text{ ms}$ median), whereas PicoClaw completes W4 in $\WFourPicoMedian\text{ ms}$ median with an $\text{EDP}$ of $\WFourPicoEDP\text{ J}\cdot\text{s}$ ($\WFourEDPReductionPct\%$ lower EDP), demonstrating significant stochastic effect sizes ($d = \WFourCliffsDelta$, $\hat{A}_{12} = \WFourAOneTwo$, adjusted $p \WFourAdjP$) by avoiding 54-tool catalog prompt bloat. Under Regime B with amortized prefill (unified single-session collection across all 5 arms in W2 and W4, with the earlier two-session collection preserved in \texttt{warm\_cache\_trials\_two\_session\_backup.jsonl} for full auditability), equalized 15-tool arms converge closely in latency and EDP ($1027.76\text{ J}\cdot\text{s}$ for Go Native, $1004.28\text{ J}\cdot\text{s}$ for Python 3.12, and $967.24\text{ J}\cdot\text{s}$ for Node.js Minimal) while remaining $41.6\%\text{ to }45.1\%$ lower in EDP than the unpruned 54-tool catalog ($1760.40\text{ J}\cdot\text{s}$). Notably, while CPython records higher raw kernel \texttt{proc\_billed\_energy} units ($84{,}819$ vs. $7{,}050$ XNU units for Go in W4), our isolated SMC rail validation (Section~\ref{sec:energy_bandwidth_deconvolution}) demonstrates that \texttt{ri\_billed\_energy} is an uncalibrated scheduler QoS proxy ($r = -0.0510$) rather than a valid Joule estimator.
\end{enumerate}

\subsection{Two-Stage Process Energy Deconvolution and Analytical \& Empirical Memory Bandwidth Estimation}
\label{sec:energy_bandwidth_deconvolution}
To isolate per-process orchestrator energy on Apple Silicon Unified Memory Architecture (UMA) where electrical shunts instrument aggregate package rails, we executed a two-stage hardware characterization protocol combining (i) phase-isolated tool benchmarking directly on the Apple SMC \texttt{CPU Power} rail with GPU idle alongside paired baseline subtraction ($\Delta E_{\text{net}}$) against \texttt{neural\_baseline}, and (ii) empirical validation of Darwin XNU kernel \texttt{proc\_pid\_rusage} counters against physical SMC Joules. Table~\ref{tab:energy_bandwidth_deconvolution} reports the empirical findings across 120 isolated CPU trials and deconvolution over 1,200 evaluated campaign trials.

\input{../results/publication_campaign/tables/table_energy_bandwidth_deconvolution.tex}

Direct physical measurement on the Apple SMC \texttt{CPU Power} rail during isolated local dispatch with the Metal GPU quiescent ($P_{\text{GPU}} \approx 0\text{ W}$) captures the true marginal electrical cost of host orchestration (reported with 95\% bootstrap confidence intervals over 2,000 resamples): in the 3-tool chain (W2), compiled Go consumes $1.252\text{ mJ/op}$ (95\% CI $[1.224, 1.280]$), CPython consumes $1.000\text{ mJ/op}$ ($[0.961, 1.041]$), and Node.js V8 requires $0.196\text{ mJ/op}$ ($[0.192, 0.200]$ Minimal) and $0.178\text{ mJ/op}$ ($[0.175, 0.181]$ Full). In vector similarity search (W3, 10,000 documents), compiled Go consumes $136.62\text{ mJ/op}$ ($[134.97, 138.30]$), OpenClaw Minimal requires $45.67\text{ mJ/op}$ ($[44.43, 46.97]$), OpenClaw Full requires $44.36\text{ mJ/op}$ ($[43.52, 45.22]$), and Python/NumPy consumes $34.08\text{ mJ/op}$ ($[31.66, 36.61]$). Crucially, cross-validating Darwin XNU's \texttt{ri\_billed\_energy} counter against physical SMC \texttt{CPU Power} rail Joules ($E_{\text{CPU, net}}$) across all 120 isolated trials establishes a formal \textbf{Negative Result}: \texttt{ri\_billed\_energy} exhibits zero global linear correlation with true CPU energy ($r = -0.0510, p = 0.580$; intra-agent $r = -0.10$ for Go, $-0.08$ for Python, and $+0.07$ for Node.js Minimal) and a negative centered coefficient of determination ($\text{OLS } R^2 = -0.676$ vs. the sample mean), indicating that uncalibrated XNU billing units perform worse than predicting the mean and overestimate CPython energy by $10\text{--}30\times$ due to internal XNU scheduler QoS/thread-weighting heuristics, corroborating Fahad et al.~\cite{fahad2019comparative}. Consequently, we reject \texttt{ri\_billed\_energy} as a Joule estimator and establish three validated physical CPU energy regressors: execution duration (\texttt{t\_exec\_ms}: $r = 0.992, \text{OLS } R^2 = 0.949$; intra-agent $\text{corr}(t, E_{\text{CPU, net}}) = 1.00$ for Go, $0.99$ for Node-Minimal, and $0.85$ for Python), retired CPU instructions (\texttt{proc\_instructions}: $r = 0.985, \text{OLS } R^2 = 0.955$), and core cycles (\texttt{proc\_cycles}: $r = 0.991, \text{OLS } R^2 = 0.945$). Using exclusively the direct physical SMC \texttt{CPU Power} rail dispatch energy ($E_{\text{CPU, net}}^{\text{dispatch}}$) divided by Regime B net task energy ($E_{\text{net, task}}$):
\begin{equation}
\Phi_{\text{energy, orch}} = \frac{E_{\text{CPU, net}}^{\text{dispatch}}}{E_{\text{net, task}}}
\end{equation}
we confirm that under amortized KV-cache reuse (Regime B), true host orchestrator CPU energy represents merely $0.04\% / 1.42\%$ ($3.76\text{ mJ} / 8.86\text{ J}$ in W2; $136.62\text{ mJ} / 9.64\text{ J}$ in W3) for PicoClaw (Go Native), $0.03\% / 0.34\%$ ($3.00\text{ mJ} / 9.70\text{ J}$ in W2; $34.08\text{ mJ} / 9.92\text{ J}$ in W3) for PythonNative, $0.01\% / 0.49\%$ ($0.59\text{ mJ} / 9.95\text{ J}$ in W2; $45.67\text{ mJ} / 9.38\text{ J}$ in W3) for OpenClaw Minimal, and $0.01\% / 0.30\%$ ($0.53\text{ mJ} / 11.00\text{ J}$ in W2; $44.36\text{ mJ} / 14.74\text{ J}$ in W3) for OpenClaw Full.

Analytical and empirical memory bandwidth estimation across the unified 120~GB/s LPDDR5X bus is modeled via:
\begin{equation}
\text{BW}_{\text{host, W3}} = \frac{S_{\text{RAG}}}{T_{\text{RAG}}}, \quad \text{BW}_{\text{decode}}(N) = \frac{S_{\text{active\_weights}} + S_{\text{KV}}(N)}{\text{ITL}_{\text{decode}}(N)}, \quad \text{with } \text{ITL}(N) = \text{ITL}_0 + \alpha_{\text{kv}} \cdot N
\end{equation}
In host vector search (W3), streaming the $S_{\text{RAG}} = 15.75\text{ MB}$ projection weights and document embeddings achieves $0.67\text{ GB/s}$ in Go, $1.80\text{ GB/s}$ in Node.js Minimal ($1.82\text{ GB/s}$ in Full), and $2.04\text{ GB/s}$ in Python. During autoregressive neural decoding on the Metal GPU (\texttt{batch\_size=1}), naive estimation using total GGUF file size ($S_{\text{file}} = 2.019\text{ GB} \div \text{ITL}$) creates an apparent physical artifact exceeding 100\% ($103\%\text{--}105\%$ or $120.5\text{--}123.8\text{ GB/s}$) in short contexts (e.g., $N=60$, $\text{ITL} = 16.76\text{ ms}$). Physical tensor inspection of \texttt{Llama-3.2-3B-Instruct-Q4\_K\_M} decomposes the $2.019\text{ GB}$ file into $S_{\text{active\_weights}} = 1.688\text{ GB}$ across the 28 dense Transformer layers (\texttt{blk.*}) and output norm ($83.61\%$ of the file) and $S_{\text{emb}} = 0.323\text{ GB}$ for the vocabulary embedding matrix ($128{,}256 \times 3{,}072$), which undergoes a sparse single-vector lookup ($\sim 3\text{ KB}$ per decode step) rather than dense streaming. Furthermore, decode latency scales affinely with context length $N$ due to streaming the Grouped Query Attention KV-cache ($S_{\text{KV}}(N) = N \cdot 114.688\text{ KB}$, where each token expends $28\text{ layers} \times 2\text{ (K+V)} \times 8\text{ heads} \times 128\text{ dim} \times 2\text{ bytes}$). Fitting this affine model over 480 physical evaluations ($N \in [60, 13216]$) yields $\text{ITL}_0 = 17.12\text{ ms}$ (zero-context baseline, 95\% CI $[17.04, 17.19]\text{ ms}$) and marginal KV streaming cost $\alpha_{\text{kv}} = 0.939\,\mu\text{s/tok}$ (95\% CI $[0.926, 0.951]\,\mu\text{s/tok}$, two-point extreme delta $[29.61 - 16.90]\text{ ms} / [13216 - 60]\text{ tok} = 0.966\,\mu\text{s/tok}$, $R^2 = 0.9781$, $p < 10^{-15}$), matching the physical time ($0.972\,\mu\text{s}$) required to stream $114.688\text{ KB}$ of KV cache over the $120\text{ GB/s}$ bus. Recomputing active bandwidth $[S_{\text{active\_weights}} + S_{\text{KV}}(N)] \div \text{ITL}(N)$ across all regimes and context tiers yields a median of $102.4\text{ GB/s}$ ($85.3\%$) and a bounded physical range of $99.0\text{--}108.5\text{ GB/s}$ ($82.5\%\text{--}90.4\%$ of the 120~GB/s ceiling; maximum observed trial $113.04\text{ GB/s}$ / $94.2\%$), with zero cells exceeding the physical memory bus ceiling. We emphasize that this represents an analytical-empirical Roofline decomposition \cite{williams2009roofline} aligning closely with empirical memory bus saturation ceilings on unified SoC architectures ($\approx 85\%\text{--}88\%$).

\section{Impact}
\label{sec:impact}
This benchmark suite provides the research and systems engineering communities with an open, reproducible testbed to isolate and quantify AI agent orchestration runtime delay. By decoupling client dispatch and schema serialization delays from neural model latency, the suite enables systems researchers to evaluate language runtime trade-offs across Go, Node.js V8, Bun JSC, and CPython under deterministic tool-use loops \cite{yao2023react, kwon2023vllm}. The framework's modular adapter architecture facilitates integrating new agent runtimes or execution environments (e.g., Rust, Zig, or Julia) with approximately 35--90 lines of code ($\sim 90$ lines for the native Bun JSC adapter). Furthermore, the multi-tier telemetry approach---combining unprivileged process counters with non-intrusive Apple SMC, Linux RAPL, and NVIDIA NVML electrical sampling---provides an extensible foundation for benchmarking local AI systems under power and thermal constraints \cite{barroso2007case, you2023zeus, fahad2019comparative}.

\subsection{Empirical Architectural Decision Rules}
Based on our empirical benchmark campaigns across Go, Node.js V8, Bun JSC, and CPython runtimes under single-model local inference (\texttt{Meta-Llama-3.2-3B-Instruct Q4\_K\_M} on \texttt{llama-server}) across Apple Silicon UMA and x86\_64 platforms, we synthesize four architectural decision rules for edge agent deployment:
\begin{enumerate}
    \item \textbf{Ephemeral CLI / Cold-Start Invocation:} For short-lived CLI utilities, serverless functions, or bursty edge triggers, native compiled Go binaries provide a $3.81\times$ faster mean startup latency ($9.74\text{ ms}$ vs. $37.15\text{ ms}$ for Node.js V8; median $3.46\times$, $9.67\text{ ms}$ vs. $33.48\text{ ms}$ in \texttt{hyperfine\_cold\_start.json}) and $7.29\times$ faster isomorphic worker initialization ($3.04\text{ ms}$ vs. $22.15\text{ ms}$ for Node.js and $49.32\text{ ms}$ for Python in \texttt{hyperfine\_worker\_version.json}), eliminating interpreter and runtime bootstrap delays.
    \item \textbf{Memory-Constrained Unified Memory (UMA) / Multi-Agent Edge:} On embedded devices and shared UMA SoCs where CPU and GPU contend for the same physical memory bus, Go native reduces peak physical DRAM allocation (\texttt{proc\_peak\_phys\_mb}) by $\PeakPhysLeanerRatio\times$ on global average ($\PicoPeakPhysMean\text{ MB}$ vs. $\OpenMinPeakPhysMean\text{ MB}$ for Node.js V8; ranging from $4.2\text{--}45.5\text{ MB}$ in Go vs. $37.5\text{--}67.1\text{ MB}$ in Node.js V8 across workloads), preserving physical DRAM capacity for model weights and KV-cache slots.
    \item \textbf{Persistent Daemons with Warm KV-Cache and Compact Schemas ($\le 15$ tools):} When running persistent services with verified prefix caching ($\text{Cache Hit} \ge 97.6\%$) and lean schemas, compiled Go, Python, Node.js V8, and native Bun (JavaScriptCore) task latency differs by only \DeviationNeuralMin{} to \DeviationNeuralMax{} from the direct neural baseline ($\Phi_{\text{orch}} \in [\PhiOrchFifteenMin{}, \PhiOrchFifteenMax{}]$). Because independent inter-session latency drift exceeds these small intra-session differences in W1, W2, and W4, wall-clock task latency across runtimes is statistically indistinguishable across sessions (except in compute-bound W3 where SIMD/BLAS routines outperform scalar Go loops by $5.6\%\text{--}5.8\%$), allowing runtime selection to prioritize ecosystem libraries and host memory constraints.
    \item \textbf{Large Enterprise Tool Catalogs ($\ge 50$ tools):} When scaling to broad enterprise tool sets, the primary performance bottleneck shifts to super-linear attention prefill on the GPU ($\alpha \approx 1.23$) rather than host orchestration. Mitigating this bottleneck requires deterministic KV-cache slot reuse or enabling active schema pruning via our built-in Zero-Copy Dynamic Tool-RAG Schema Pruner ($54 \rightarrow \text{Top-}5$ tools in $<0.35\text{ ms}$, eliminating $>85\%$ of cold-prefill latency and energy overhead).
\end{enumerate}

\subsection{Threats to Validity and Methodological Limitations}
\label{sec:threats_to_validity}
To ensure objective interpretation and prevent over-generalization of our empirical findings, we explicitly document eleven methodological boundaries and threats to validity:
\begin{enumerate}
    \item \textbf{Statistical Limitations and Serial Autocorrelation Control:} Sequential trials in physical benchmark campaigns display positive serial autocorrelation ($r_1 > 0$) driven by runtime state and operating system caching. Simulations of AR(1) processes at $n=30$ demonstrate that first-order analytical variance adjustment ($n_{\text{eff}}$ / VIF) fails to maintain exact 5\% Type~I error control (retaining ~8.2\% false positives at $r_1=+0.4$ and ~12.7\% at $r_1=+0.7$). Consequently, our pipeline establishes contiguous block permutation ($B=5000$) with adaptive block length $b \in \{3, 5, 8, 12\}$ as the primary two-sample inference mechanism. Dual-session replication via Moving Block Bootstrap ($b=3$, $B=10{,}000$) TOST was evaluated across block lengths $b \in \{2, 3, 5, 8, 12, \text{adaptive}\}$ (documented in \texttt{audit\_export/tost\_block\_sensitivity.csv} and \texttt{tost\_block\_sensitivity\_expanded.csv}): decisions remain invariant across $b \in \{2, 3, 5\}$ (71 Equivalent, 24 Inconclusive), altering slightly at $b=8$ (72 Equivalent) and $b=12$ (74 Equivalent; 3 total decisions change between $b=3$ and $b=12$). Deterministic AR(1) simulations (\texttt{audit\_export/mbb\_coverage_and\_tost\_power.csv}) explicitly document MBB 90\% CI coverage (~70--92\% across $r_1 \in [-0.7, +0.7]$) reflecting empirical undercoverage at $n=30$ in the absence of studentized or double-bootstrap corrections, alongside low statistical power under positive serial dependence ($3.4\%$ at $r_1=+0.4$ and $2.0\%$ at $r_1=+0.7$). Furthermore, pairs are formed by chronological trial index (\texttt{rep}), which assumes stable sequence ordering; a parallel proportional SESOI analysis ($\Delta_{\text{prop}} = \max(2.0\text{ ms}, 0.10 \times |\text{median}(c_1)|)$) is documented alongside the fixed $\pm 5.0\text{ ms}$ threshold.
    \item \textbf{Linux Physical Throttling Stratification:} Hardware counter stratification across all 172 Linux experimental cells (\texttt{audit\_export/linux\_throttling\_stratification.csv}) reveals that across the 172 Linux cells, the median package temperature difference between high- and low-throttling trials is $0.0^\circ\text{C}$ (mean $-0.06^\circ\text{C}$, range $-2.5^\circ\text{C}$ to $+4.0^\circ\text{C}$), and median latency elongation is $-0.17\%$ (mean $-0.22\%$, range $-3.08\%$ to $+1.55\%$). Therefore, package thermal throttling events do not account for positive serial autocorrelation ($r_1 > 0$) on Linux in these empirical runs, and the thermal throttling hypothesis is not confirmed.
    \item \textbf{Thermal and Inter-Session Directional Drift Boundary:} Across multi-hour benchmark campaigns on physical testbeds, system state introduces non-random directional drift. As quantified in \texttt{audit\_export/inter\_session\_drift\_test.csv}, in Linux Regime A, Session 2 was consistently faster than Session 1 in 29 out of 30 matched condition cells (median drift $2.21\%$, maximum $44.85\%$ in \texttt{python\_native} W5; binomial sign test $p < 10^{-7}$), whereas on Windows 11 NVIDIA the median drift was $0.44\%$ (maximum $1.93\%$). Because trials between sessions are not exchangeable under a null of zero drift, end-to-end task latency contrasts smaller than inter-session drift hold solely \textit{intra-session}. Only effects that exceed this floor or operate purely on host CPU logic---specifically W3 Vector RAG ($+5.41\%$ to $+5.85\%$ scalar Go penalty vs. SIMD/BLAS), 54-tool vs. 15-tool schema bloat ($>21\%\text{--}87\%$), and host microarchitectural metrics ($T_{\text{orch}}$, \texttt{Peak Phys RAM}, and CPU cycles)---generalize invariantly across sessions.
    \item \textbf{Retired Instructions as Runtime Activity Metric:} Hardware PMU retired instruction counts capture total user-space and runtime activity (including language interpreter loops, garbage collection cycles, JIT compiler deoptimizations, and scheduler bookkeeping) rather than orchestrator business logic alone. For example, in Linux Workload W2, CPython retires $2{,}544\text{M}$ instructions ($78.5\times$ more than Go), yet achieves an orchestrator dispatch latency ($T_{\text{orch}} = 30.22\text{ ms}$) lower than Node.js V8 ($35.53\text{ ms}$), demonstrating that instruction counts measure runtime execution volume rather than direct wall-clock delay.
    \item \textbf{Diagnostic Segregation of W5 Python Prototype:} In Workload W5 on Linux x86\_64, the \texttt{python\_native} prototype exhibited an anomalous orchestrator latency ($1{,}416.20\text{ ms}$ in Session 1 vs. $781.01\text{ ms}$ in Session 2, a $44.85\%$ directional drift). Because this prototype utilized synchronous loopback dispatch under unoptimized SQLite transaction framing, its execution is diagnostically segregated in Table~\ref{tab:w5_enterprise_workload} without asserting causal root-cause mechanisms pending dedicated profiler trace analysis.
    \item \textbf{Model Scale and Quantization Dependence:} Our empirical evaluation employs \texttt{Llama-3.2-3B-Instruct} (\texttt{Q4\_K\_M}, $2.019\text{ GB}$ weights). Scaling to larger foundation models (8B--70B parameters) or higher-precision formats (Q8\_0/FP16) increases neural prefill and decode latency ($T_{\text{neural}}$) proportionally to weight volume and layer depth, which further compresses the relative orchestrator overhead fraction ($\Phi_{\text{orch}} = T_{\text{orch}} / T_{\text{task}}$) while leaving absolute client-side dispatch delay ($T_{\text{orch}}$) and resident DRAM footprint (\texttt{proc\_peak\_phys\_mb}) invariant.
    \item \textbf{Apple Silicon Unified Memory Architecture (UMA) Specifics:} The reference UMA campaign (Regimes A and B, prefill regression, Tool-RAG same-session ablation, and SMC energy deconvolution) was conducted on an Apple Mac mini M4 featuring $24\text{ GB}$ of shared LPDDR5X UMA memory ($120\text{ GB/s}$ theoretical peak), complemented by the three physical x86\_64 testbed nodes (Linux x86\_64 RTX 3050, Windows 11 RTX 3050, and Windows 10 Intel HD Graphics 4600) detailed in Item~10 below. Unlike discrete PCIe GPU topologies on x86\_64 servers---where host-to-device DMA transfers across the PCIe bus incur explicit copy latency and separate DRAM/VRAM allocation---UMA shares a single physical memory pool between CPU and GPU. Consequently, client-side orchestrator heap bloat on UMA directly reduces the physical DRAM available for neural KV-cache slots and model weights.
    \item \textbf{KV-Cache Slot Isolation and Prefix Invalidation Protocol:} Regime B evaluates deterministic single-slot execution (\texttt{-np 1}) with block-isolated priming (3 warmups + 30 consecutive trials per condition) to measure steady-state prefix reuse ($\text{Cache Hit} = 97.7\%\text{--}100.0\%$). In multi-tenant or interleaved multi-agent servers where distinct system prompts contend for a single KV-cache slot without RadixAttention tree sharing \cite{kwon2023vllm} or multi-slot partitioning (\texttt{-np > 1}), frequent prefix invalidation degrades execution toward Regime A cold-prefill behavior.
    \item \textbf{Indirect Process Energy Attribution and Negative Validation of \texttt{ri\_billed\_energy}:} Because hardware power shunts on UMA SoCs instrument aggregate package rails rather than individual POSIX PIDs, concurrent CPU--GPU execution cannot be physically separated at the analog sensor level \cite{fahad2019comparative, you2023zeus}. Our phase-isolated calibration on the Apple SMC \texttt{CPU Power} rail formally refutes Darwin XNU's \texttt{ri\_billed\_energy} counter as a valid physical Joule proxy ($r = -0.0510, p = 0.580$, centered $\text{OLS } R^2 = -0.676$), demonstrating that uncalibrated kernel billing units reflect QoS scheduler heuristics rather than true energy. Accurate host energy attribution requires either phase-isolated SMC \texttt{CPU Power} rail integration with the GPU idle ($\Phi_{\text{energy, orch}} \in [0.01\%, 1.42\%]$) or our validated physical regressors (\texttt{t\_exec\_ms}, \texttt{proc\_instructions}, and \texttt{proc\_cycles}, $R^2 = 0.945\text{--}0.955$).
    \item \textbf{Cross-Hardware Generalization and Quad-Platform Validation:} To verify the cross-platform validity of our architectural findings, the software harness provides native telemetry adapters across four distinct physical hardware/OS platforms: (i) Apple Silicon M4 (macOS Darwin ARM64) via Apple SMC and XNU \texttt{libproc}, (ii) Linux x86\_64 (Ubuntu 26.04 LTS, kernel 7.0) on a Dell G15 5520 via Intel RAPL \texttt{powercap}, NVIDIA NVML, and PMU \texttt{perf\_event\_open(2)}, (iii) Windows 11 x86\_64 (Build 26200) on a Dell G15 5520 via Win32 \texttt{QueryProcessCycleTime}, PSAPI \texttt{GetProcessMemoryInfo}, and NVML DLL, and (iv) Windows 10/11 x86\_64 on an MSI Z97 system with an Intel Core i7-4790K and integrated Intel HD Graphics 4600 (UMA shared system RAM) via unprivileged Win32 PSAPI process limits. On Workload W2 (Table~\ref{tab:quad_platform_master}), compiled Go (PicoClaw) achieves consistent orchestration speedups ($T_{\text{orch}}$) over Node.js across all four operating environments: $\mathbf{4.44\times}$ on macOS M4 ($5.53\text{ ms}$ vs. $24.55\text{ ms}$), $\mathbf{5.31\times}$ on Linux x86\_64 ($6.68\text{ ms}$ vs. $35.53\text{ ms}$), $\mathbf{3.70\times}$ on Windows 11 NVIDIA ($13.11\text{ ms}$ vs. $48.55\text{ ms}$), and $\mathbf{4.91\times}$ on Windows Intel iGPU ($14.03\text{ ms}$ vs. $68.89\text{ ms}$). Hardware PMU instruction bloat reduction reaches $\mathbf{12.71\times}$ on macOS and $\mathbf{23.87\times}$ on Linux \cite{weaver2013nondeterminism}. Under our empirical evaluation protocol without synthetic extrapolation, hardware instructions on both Windows platforms are marked $\text{N/A}^*$ due to user-mode PMU counter restrictions (\texttt{CR4.PCE}), with empirical CPU cycles tracked directly via \texttt{QueryProcessCycleTime} ($45.8\text{M}$ cycles in PicoClaw vs. $528.1\text{M}$ cycles in OpenClaw Full on Windows 11 NVIDIA, a $11.54\times$ cycle ratio; and $87.8\text{M}$ vs. $1446.1\text{M}$ cycles on Windows Intel iGPU, a $16.47\times$ ratio). Furthermore, active Tool-RAG schema pruning ($54 \rightarrow \text{Top-}5$, $-87.1\%$ prompt tokens) achieves a controlled same-session W2 cold prompt-prefill speedup of $\mathbf{7.28\times}$ on macOS (measured within \texttt{tool\_rag\_mitigation\_trials.jsonl}), alongside exploratory cross-session ratios of $\mathbf{5.16\times}$ on Linux, $\mathbf{4.64\times}$ on Windows NVIDIA, and $\mathbf{9.96\times}$ on Windows Intel Graphics (referenced against each x86\_64 node's primary campaign baseline \texttt{raw\_trials.jsonl} rather than a same-session baseline; accordingly, no causal speedup claims are made for x86\_64 Tool-RAG), while Windows loopback HTTP sockets exhibit $26.63\text{ ms}$ ($26.632\text{ ms}$) latency vs. $1.88\text{ ms}$ ($1.883\text{ ms}$) in-process dispatch ($14.14\times$ Winsock overhead; Table~\ref{tab:mcp_transport_ablation}). Crucially, on the x86\_64 testbed nodes (Dell G15 under Linux and Windows 11) equipped with an NVIDIA GeForce RTX 3050 Laptop GPU (4~GB GDDR6 VRAM), neural inference operated in a hybrid offload regime (\texttt{-ngl 16}, allocating $\approx 3.0\text{ GiB}$ in the 4~GB VRAM ceiling and retaining remaining transformer layers in host DDR5 memory via AVX2 \cite{sheng2023flexgen}), entailing continuous PCIe 4.0 bus streaming saturation (empirically recorded as continuous PCIe RX traffic averaging $5{,}206\text{ MB/s}$ and peaking at $11{,}273\text{ MB/s}$ during prompt prefill bursts). Consequently, Regime~B combines distinct offload configurations (\texttt{-ngl 99} UMA vs. \texttt{-ngl 16} PCIe hybrid vs. shared DDR3 iGPU) and does not permit causal cross-platform comparisons of absolute neural latency. On the Intel Graphics node, host package energy and discrete VRAM are marked $\text{N/A}^{**}$ due to unprivileged user-mode execution on shared host memory aperture without kernel MSR RAPL access, and its workload scope was restricted to W2, W5, and W2 Tool-RAG because shared DDR3-1600 prefill latency spanned $53.5\text{--}226.7\text{ s/trial}$ (making full W1--W4, 10-turn W4, KV-thrashing, and MCP campaigns across two 30-rep sessions prohibitively slow and vulnerable to thermal/OS drift). Similarly, Bun (JavaScriptCore) was evaluated in both Cold and Warm regimes exclusively on x86\_64 nodes in the consolidated quad-platform matrix (marked $\text{N/A}^{\parallel}$ on macOS) because it was introduced as a secondary JavaScript-engine ablation after the Apple Silicon M4 primary campaign froze, with supplementary macOS Warm Session~2 Bun measurements preserved in \texttt{inter\_session\_trials.jsonl}. All empirical datasets originate from clean from-scratch runs without partial data reuse. Finally, as an architectural horizon for benchmark v2.0, Large Multimodal Models (LMMs / Vision) introduce dense image-patch token expansions and 2D spatial cross-attention layers, shifting orchestrator overhead toward high-throughput zero-copy visual framebuffer ingestion.
    \item \textbf{External Validity Boundaries and Third-Party Licensing:} Beyond hardware topology asymmetry, four explicit external validity boundaries govern interpretation of these empirical measurements: (i) \textit{single 3B quantized model}---all campaigns evaluate \texttt{Meta-Llama-3.2-3B-Instruct} (\texttt{Q4\_K\_M}, governed by the Meta Llama 3.2 Community License; larger 8B--70B models alter $T_{\text{neural}}$ and compress $\Phi_{\text{orch}}$); (ii) \textit{single inference server backend}---all local serving uses \texttt{llama-server} (\texttt{llama.cpp}, MIT License), so serving engines with continuous batching or RadixAttention (e.g., vLLM \cite{kwon2023vllm}) will exhibit different KV-cache dynamics; (iii) \textit{synthetic deterministic workloads}---workloads W1--W5 use controlled, reproducible tool chains, 384-D vector search, and SQLite fixtures rather than open-ended production user traffic; and (iv) \textit{heterogeneous platform sensors}---electrical energy and PMU telemetry differ structurally across Apple SMC (on-die SoC), Linux/Windows Intel RAPL + NVIDIA NVML (CPU package + dGPU), and Windows Intel HD 4600 user-mode PSAPI/\texttt{QueryProcessCycleTime} ($\text{N/A}^{**}$ energy), restricting absolute power/energy comparisons to within-node contrasts. All reference agents evaluated under the \texttt{PicoClaw} and \texttt{OpenClaw} names are clean-room academic implementations isolated for systems benchmarking.
\end{enumerate}

\subsection{Model Context Protocol (MCP) Live Transport and Quantization Scaling}
\label{sec:mcp_and_quant}
To evaluate orchestrator overhead under emerging agent protocol standards, we conducted two targeted physical ablations on the Apple M4:
\begin{enumerate}
    \item \textbf{Live Model Context Protocol (MCP) Transport Ablation:} Following emerging Model Context Protocol (MCP) standards for agent-tool communication, we evaluated tool invocation across three physical transport boundaries in W2 Warm Cache ($n=15$ repetitions, Table~\ref{tab:mcp_live_transport}): in-process function calls ($0.90\text{ ms}$ Go, $1.63\text{ ms}$ Node.js), persistent \texttt{stdio} pipe IPC via JSON-RPC 2.0 ($1.81\text{--}1.90\text{ ms}$), and local loopback HTTP ($3.15\text{--}3.22\text{ ms}$). Across all configurations, external IPC overhead ($\Phi_{\text{orch}} \le 0.18\%$) remains negligible relative to neural token decode latency.
    \item \textbf{Extreme Quantization Scaling Ablation:} Evaluating \texttt{Llama-3.2-3B-Instruct} across 2-bit (Q2\_K, $1.025\text{ GB}$ active weights), 3-bit (Q3\_K\_M, $1.348\text{ GB}$), and 4-bit (Q4\_K\_M, $1.688\text{ GB}$) on the Metal GPU (Table~\ref{tab:quantization_scaling}) confirms that generation throughput scales inversely with active weight footprint ($51.0\text{ tok/s}$ at 2-bit vs. $45.0\text{ tok/s}$ at 4-bit). In all bit-widths, the memory bus remains the universal bottleneck ($52.3\text{--}75.9\text{ GB/s}$), while orchestrator overhead remains $\le 0.38\%$ for compiled Go and $\le 2.35\%$ for commercial enterprise frameworks (LangChain Core).
    \item \textbf{Automated Verification Gatekeeper:} To prevent invalid or synthetic submissions in open replication, we integrated an automated submission gatekeeper (\texttt{scripts/audit\_submission\_gatekeeper.py}) adhering to systems benchmarking and artifact verification principles~\cite{kalibera2013rigorous, hoefler2015scientific}. The gatekeeper cryptographically validates all 9 schema invariants and enforces an analytical Roofline constraint based on active model weights ($\text{BW}_{\text{active}} \le 120.0\text{ GB/s}$, with median observed active bandwidth $102.4\text{ GB/s}$ [85.3\% peak]). Note that under a naive computation ($2.019\text{ GB} / \text{ITL}$), 11 out of 150 trials in macOS Regime A exceed $120\text{ GB/s}$ (median $112.5\text{ GB/s}$), demonstrating that naive computation does not reflect physical memory streaming in dense layers. The gatekeeper successfully verifies all $3{,}774$ publication records in \texttt{data/gatekeeper\_audit\_certificate.json}.
\end{enumerate}

\section{Conclusions}
\label{sec:conclusions}
The \texttt{picoclaw-vs-openclaw-benchmark} framework delivers an open, extensible methodology and active schema-pruning toolkit for systems-level evaluation of AI agent orchestrators on unified memory microarchitectures. Our empirical findings demonstrate that under equalized tool schemas and equivalent generation token counts, end-to-end task latency across Go, Node.js V8, native Bun (JavaScriptCore), and Python exhibits near-parity within sessions ($< 6\%$ variance) as package power saturates near 16~W on the Metal GPU, while independent inter-session replication ($n=30$) confirms that cross-session thermal/clock drift ($\sim 3\%\text{--}10\%$) exceeds intra-session runtime differences in W1, W2, and W4 (with W3 vector RAG favoring SIMD/BLAS over scalar Go loops by $5.6\%\text{--}5.8\%$). Crucially, native compiled Go execution (\texttt{PicoClaw}) provides consistent, session-invariant host microarchitectural advantages over managed Node.js V8 (\texttt{OpenClaw}) across I/O- and schema-bound workloads (W1, W2, W4, and W5): lower isolated orchestrator latency ($T_{\text{orch}}$ across all four hardware/OS platforms in W2, ranging from $3.70\times$ to $5.31\times$ faster than OpenClaw Full), $\InstructionOverheadRatio\times$ fewer retired CPU instructions on Apple M4 ($23.87\times$ on Linux x86\_64), $\CyclesOverheadRatio\times$ fewer CPU cycles, $3.81\times$ faster CLI cold-start ($7.29\times$ in minimal worker initialization), and a $\PeakPhysReductionMinRatio\times$ to $\PeakPhysReductionMaxRatio\times$ lower physical DRAM footprint. Crucially, however, an explicit \textbf{ranking inversion occurs in compute-bound Vector RAG (W3)}: because our clean-room Go worker performs scalar dot-product loops over 10,000 embeddings, \texttt{PicoClaw} is outperformed in W3 client dispatch latency ($T_{\text{orch}}$) by vectorized SIMD/BLAS routines in \texttt{PythonNative} (NumPy/Accelerate/OpenBLAS: $21.52\text{ ms}$ vs. $36.83\text{ ms}$ Cold on macOS M4; $35.20\text{ ms}$ vs. $45.09\text{ ms}$ Cold on Linux) and \texttt{Bun} JavaScriptCore ($28.32\text{ ms}$ Cold on Linux; $39.99\text{ ms}$ vs. $49.68\text{ ms}$ Cold on Windows 11; $18.09\text{ ms}$ Warm Session~2 on macOS), demonstrating that runtime ranking depends on whether host work is dispatch/I/O-bound or numerical SIMD-bound. Furthermore, our hardware validation refutes uncalibrated XNU \texttt{ri\_billed\_energy} counters as a Joule proxy ($r = -0.0510, R^2 = -0.676$) in favor of direct SMC \texttt{CPU Power} rail isolation ($\Phi_{\text{energy, orch}} \le 1.42\%$) and validated instruction/time regressors ($R^2 \ge 0.949$), while our active Zero-Copy Tool-RAG Schema Pruner eliminates $>85\%$ of 54-tool catalog prefill bloat in under $0.35\text{ ms}$. Through standardized workload tiers, non-parametric statistics adjusted for serial dependence, and portable reviewer dry-runs, this software establishes a reproducible foundation for evaluating edge agent orchestration systems.
